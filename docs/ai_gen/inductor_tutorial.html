3. 融合的本质为什么融了就快:省带宽 + 省 launch

融合 = 把多个算子的循环体拼进同一个 kernel,中间张量留在寄存器/共享内存里,不再写回 HBM 再读回来,同时少一次 kernel launch 与算子下发。拖动滑块感受两种收益的占比变化:

不融合:读 x + 写 t + 读 t + 写 y = 8N 字节,2 次 launch
不融合
融合:读 x + 写 y = 4N 字节,1 次 launch
融合
估算耗时(device 侧,不含下发)
不融合 ≈ - ms    融合 ≈ - ms
两个 regime 的启示
大 kernel 时收益由带宽主导(中间张量省一次 HBM round-trip);小 kernel 时收益由 launch / 算子下发主导(每次少几微秒,但乘上千百个 kernel 非常可观)。Inductor 的 autotune 只保证第一类收益(见第 6 节),第二类收益靠「kernel 数单调减少」的结构性假设 + cpp_wrapper / CUDA Graph 保障。

5. 融合规则纵向融合 / 横向融合 / 模板 epilogue-prologue

5.1 纵向融合(Vertical):生产者 → 消费者

沿数据流的相邻节点合并。合法性看依赖(can_fuse_vertical,scheduler.py:10911):消费者读的缓冲必须与生产者的写逐点匹配(MemoryDep 相同索引),不能隔着未融合的中间节点,不能成环。收益看共享数据量。点击按钮逐步融合:

每步发生了什么检查

  • 依赖匹配: sum 读 t1 的索引与 gelu 写 t1 完全一致(MemoryDep 逐点对应),否则 "memory deps did not match"。
  • 无中间夹层: 生产者与消费者之间不能隔未融合节点,否则 "intermediate nodes between node1 & node2"。
  • 无环: will_fusion_create_cycle 检查;DAG 里下游融合不得打乱上游调度。
  • 共享数据 > 0: pw 链之间靠「消费者读生产者写」天然满足;为 0 时默认拒绝。
  • 收益排序: score_fusion ≈ 省掉的共享字节 + 图序邻近度,贪心从高分对开始融。
pointwise 生产者可以融入 reduction 消费者内部(reduction 的 loop 里先算 pw 再归约);反向(reduction 的输出喂点链)也合法,但输出要在 kernel 内物化,persistent reduction 下 softmax 这类「red→pw→red→pw」整条链可缩成 1 个 kernel。

5.2 横向融合(Horizontal):无依赖的平行支路

  • 两条支路互不依赖但读同一输入 → 共享数据 = x 的字节数,≥ 阈值即可融(can_fuse_horizontal,choices.py:758)。
  • 阈值 score_fusion_memory_threshold = 10 字节:省的字节太少就不值得合并循环。
  • 完全无共享数据时默认拒绝("no shared data");aggressive_fusion=True(且非 reduction)才放开 —— 放开后逐对合并或生成 combo kernel / foreach。
  • 相距太远的两支路拒融:"Nodes are too far away"(合并会让两条支路的中间结果同时存活,推高峰值显存)。
  • 对完全无关的 kernel,还有更彻底的合并形态 —— combo kernel,见 4.3。

5.3 Combo Kernel:无关 kernel 的合并执行

常规横向融合要求「有共享数据」;combo kernel(combo_kernels,默认关)是它的彻底形态:把互不依赖、shape 也可以不同的独立 kernel 在编译期拼进同一个 Triton kernel,只为摊一次 launch。

  • 代码生成:统一 grid 后用 Sequential / RoundRobin / Flatten 三种映射策略把 program id 分发到各子 kernel(triton_heuristics.py:5848),拼装逻辑在 triton_combo_kernel.py。
  • 总开关 combo_kernels=False:叠加在常规融合之上 —— 先让 4.1 / 4.2 的规则各自成 kernel,再把剩下的独立 kernel 装箱。
  • 装箱过滤:extern、模板、foreach、staged/multi-output、间接索引节点都被排除;默认最多 8 个子 kernel(combo_kernel_max_num_nodes)、250 个 buffer 参数(combo_kernel_max_num_args);combo_kernels_pointwise_only 可只收 pointwise。
  • 是否划算可实测:benchmark_combo_kernel=True 时对「合并 vs 独立」逐组实测;< 0.3 ms 的小 kernel 跳过实测直接融 —— 代码注释原话:小 kernel 几乎必然有收益但难测准(scheduler.py:12947)。注意这又是 launch 侧收益,同样不在 device-time 计量里。
  • 子 kernel 独立调优:combo_kernel_per_subkernel_blocks 让每个子 kernel 拥有自己的 XBLOCK_0 / YBLOCK_0 …,并支持编译期 per-subkernel autotune;另有峰值显存门控与调度距离门控(combo_kernel_max_distance=64)。
  • foreach 是它的特例:同 shape 的 foreach 合并早已默认启用;combo kernel 是推广到「不同 shape、不同计算」的一般情形。

5.4 模板 epilogue / prologue:GEMM 与周围点算的融合

  • epilogue(GEMM 模板路径):消费者被内联进模板的 store 区域后整体编译 + 实测裁决(benchmark_template_fusion 默认开);允许额外的 load —— bias-add 就是标准用例(模板 operand 与 epilogue operand 共用 buffer 也已处理,triton.py:3875)。需与 store 索引一致,否则 "epilogue's read and write indices differ"。✅ bias、gelu、scale、dropout(rand+mul);其余组合能否融以「编译成功 + 实测更快」为准。
  • 「一元读」的字面出处是另一条路径:自定义 Triton kernel(UserDefinedTritonKernel)的 in-place epilogue 要求消费者恰好读 1 个 buffer(该 kernel 改写的输出)、写 1 个 buffer、同索引 —— 连多读一个 bias 都会拒(scheduler.py:10575,注释:"Any other tensor/s would require additional load expressions")。普通 extern(cuBLAS)输出上则根本无法挂 epilogue("node1 is extern but not a triton kernel")。
  • prologue(prologue_fusion,OSS 默认开):模板输入上的一元、单使用者函数融进 load,否则 "template prologue can only fuse nodes with a single use"。
  • 默认(无 max_autotune)GEMM 走 cuBLAS extern,没有 epilogue 槽位,周围点算各自成 kernel;extern 是天然屏障("node2 is extern or nop")。
  • 开启 max_autotune_gemm 后,模板 + epilogue 组合在调度期实测后与 ATen 同台比较(见第 6 节)。
  • 融合规模上限:max_fusion_size = 64 是调度图 node 数;kernel 内实际串的 aten 表达式数无此硬上限(受 Triton 编译器 / SM 资源约束)。它与「融合 kernel 的算子数」是两个度量,详见 fusion_breadth_analysis.md §10。

5.5 融合评分计算器(共享字节 vs 阈值)

判定阈值:score_fusion_memory_threshold = 10 字节(横向融合);蓝=通过,橙=aggressive_fusion 放开,红=拒绝

6. Autotune对候选实现实测选优 —— 以及它保证什么、不保证什么

对同一节点的所有候选(Triton 模板的各组 tile 配置、CUTLASS、ATen/cuBLAS)编译成真 kernel 后逐个实测,取 device time 最小者(benchmark_choices,select_algorithm.py:5692)。点击模拟一次 addmm 的选型:

第二阶段:融合是否真的更快?benchmark_template_fusion = True(默认)

调度期把「模板 + epilogue 融合后的 kernel」与「不融合(模板 kernel + 独立 epilogue kernel)」都编出来实测,慢就放弃融合(scheduler.py:7394 speedup_by_fusion)。

⚠️ Autotune 保证的是 kernel device time,不是 E2E
  • 计时实现:每对 CUDA event 包住单次调用取 min(benchmarking.py:675),或直接取 kineto trace 里的 kernel 时间(do_bench_using_profiling)—— host 下发开销不在测量范围内。
  • 甚至有反向开关 autotune_cudagraph_benchmarking:把候选 capture 进 CUDA graph 再 replay 计时,「eliminates host-side dispatch overhead」,使结果贴近 cudagraph 运行环境。
  • E2E 的下发收益靠结构性假设:融合使 kernel 数单调减少 → 下发次数单调减少;真正的下发优化由 cpp_wrapper / mode="reduce-overhead"(CUDA Graph)承担。
  • 因此存在回退盲区:fused kernel GPU 略慢但省一次 launch 的场景会被否决;融合引入 host 开销(item() 同步、动态 shape 重编译)不测。pairwise 局部最优 ≠ 全局最优。

autotune 的成本与缓存

  • 候选编译 + 实测在子进程中进行(autotune_in_subproc),不污染主进程 CUDA context。
  • 结果进 autotune 本地缓存(autotune_local_cache),整图结果进 FxGraphCache;同 shape 第二次编译几乎零成本。
  • 更细粒度搜索:coordinate_descent_tuning(默认关)在预设 tile 之外逐维爬山,收益可能显著但编译时间大涨。
